# 私有知识库 RAG 问答系统 · 架构设计方案

> **项目代号**：rag-knowledge-base
> **版本**：v1.0 设计稿
> **定位**：企业内部文档智能问答，可作为简历级完整工程实践
> **LLM 接入**：通义千问 DashScope（OpenAI 兼容接口）

---

## 1. 项目目标与设计原则

### 1.1 目标

构建一套私有化部署友好的 RAG（Retrieval-Augmented Generation）问答系统，实现：

1. **知识资产沉淀**：企业内部 PDF / Word / Markdown / TXT 文档统一解析入库
2. **精准问答**：答案基于检索到的真实文档片段生成，附带来源引用（文档名 + 页码），可溯源、防幻觉
3. **可量化演进**：每个迭代阶段都有可量化的评估指标，优化有据可依

### 1.2 设计原则

| 原则 | 落地方式 |
|---|---|
| **读懂源码，不迷信封装** | LangChain 只用它薄薄一层抽象（TextSplitter / PromptTemplate / LLM 客户端），检索、拼装、引用溯源等核心逻辑自己手写，每一步数据流可见 |
| **接口先行** | FastAPI 定义清晰的 REST 契约，前端（Streamlit）只是接口的消费者，后期可换任意前端 |
| **配置与代码分离** | `.env` + Pydantic Settings 管理所有可变项（模型名、chunk 大小、Top-K），调参不改代码 |
| **渐进式向量库** | 抽象 `VectorStore` 接口，本地 Chroma 实现，后期无痛切 Milvus / pgvector |
| **全程可观测** | 结构化日志记录每次请求的检索命中、耗时、token 消耗，为阶段2评估打基础 |

## 2. 总体架构

### 2.1 架构分层

```
┌─────────────────────────────────────────────────────┐
│  展示层   Streamlit Web UI（问答页 / 文档管理页）      │
├─────────────────────────────────────────────────────┤
│  接口层   FastAPI（RESTful，Postman 可调试）           │
│           /api/upload  /api/chat  /api/documents     │
├─────────────────────────────────────────────────────┤
│  应用层   RAG 核心服务                                 │
│   ├─ ingestion  文档解析 → 清洗 → 分块 → 向量化 → 入库  │
│   └─ retrieval  查询 → 检索 → 重排 → 上下文拼装 → 生成  │
├─────────────────────────────────────────────────────┤
│  模型层   BGE-Large-ZH (Embedding)                    │
│           DashScope qwen-plus / qwen-turbo (LLM)      │
│           阶段2: BGE-Reranker (Cross-Encoder)        │
├─────────────────────────────────────────────────────┤
│  存储层   Chroma（向量+元数据） · SQLite（文档索引）    │
│           阶段3: Milvus / pgvector + PostgreSQL       │
└─────────────────────────────────────────────────────┘
```

### 2.2 核心数据流

**入库链路（离线）**

```
文档上传 → 后缀路由解析器 → 统一文本抽取（带页码定位）
        → 清洗（去页眉页脚/多余空白） → RecursiveCharacterTextSplitter 分块
        → BGE 向量化（batch） → Chroma upsert（含 metadata）
```

**问答链路（在线）**

```
用户提问 → Embedding → Chroma 相似度检索 Top-K
        → 组装 Prompt（system 指令 + 引用编号片段 + 问题）
        → 通义千问生成 → 后处理（引用编号映射回文档名+页码）
        → 返回答案 + sources 列表 → 前端渲染（答案高亮引用）
```

## 4. 阶段1 · 基础版详细设计（1-2 周）

### 4.1 文档解析（parsers.py）

统一解析器接口，按后缀路由：

```python
class ParsedDoc:
    pages: list[Page]      # Page(text, page_no) —— 保留页码用于引用溯源

# PDF: PyMuPDF (fitz) —— 逐页提取 page.get_text()
# DOCX: python-docx —— 无页码概念，按段落块切伪页（每 N 段为一页）
# MD:   markdown 库转纯文本 + 标题层级保留（标题作为 chunk 上下文前缀）
# TXT:  直接读取，整文件一"页"
```

**关键细节**：
- PDF 中文乱码：fitz 对扫描件返回空文本 → 检测空页率 > 30% 时提示"疑似扫描件，需要 OCR（阶段3）"
- Markdown 解析时把 `# 标题` 注入每个 chunk 的前缀（`context_prefix`），保证 chunk 脱离原文仍有语义

### 4.2 文本分块（chunker.py）

用 LangChain 的 `RecursiveCharacterTextSplitter`，参数进 `.env`：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `CHUNK_SIZE` | 500 | BGE-Large 最佳输入 512 token，中文按字符算 500 是甜点 |
| `CHUNK_OVERLAP` | 80 | 约 16% 重叠，缓解语义截断 |
| 分隔符优先级 | `["\n\n", "\n", "。", "！", "？", "；", "，", " "]` | 中文标点在列，尽量在自然句边界切 |

**每个 chunk 的 metadata 结构**：

```json
{
  "doc_id": "uuid",
  "doc_name": "员工手册v3.pdf",
  "page_no": 12,
  "chunk_index": 45,
  "context_prefix": "第3章 薪酬福利"   // MD/DOCX 的标题路径
}
```

### 4.3 向量化与入库

- **Embedding**：`BAAI/bge-large-zh-v1.5`（本地 HuggingFace 加载，FP16 约 1.3GB 显存 / CPU 可跑但慢）。**单例模式**加载，避免每次请求重载
- bge-large-zh 使用时查询侧**无需** instruction 前缀（bge v1.5 起 query/passage 对称），直接 encode
- **批量入库**：`batch_size=32`，带 tqdm 进度，入库后返回 `{doc_id, chunk_count}`
- **Chroma**：`PersistentClient` 落盘到 `data/chroma/`，`cosine` 空间（`hnsw:space=cosine`，默认是 L2，必须显式改）

### 4.4 问答与引用溯源（pipeline.py）

**引用编号协议**（本项目的核心小设计）：

```
System Prompt 片段：
"以下是从知识库检索到的资料，每段前面有编号 [1] [2] ...
回答时请在对应句子末尾标注引用编号，格式如：年假为 15 天[1]。
如果资料不足以回答，请直接说明，不要编造。"

Context:
[1] (员工手册v3.pdf, 第12页) 员工入职满一年后享有 15 天年假……
[2] (考勤制度.docx, 第3页) ……
```

后处理时正则提取 `[n]` → 映射回 `sources: [{doc_name, page_no, snippet}]` 返回给前端，前端把引用渲染成可点击的悬浮卡片。

### 4.5 FastAPI 接口定义

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/documents/upload` | multipart 上传，支持多文件，返回 doc_id 列表 |
| GET | `/api/documents` | 文档列表（名称、chunk 数、入库时间） |
| DELETE | `/api/documents/{doc_id}` | 删除文档及其所有向量（按 metadata 过滤删除） |
| POST | `/api/chat` | `{question, top_k?, stream?}` → 答案 + sources；`stream=true` 时 SSE 流式 |
| GET | `/api/health` | 存活检查（含模型加载状态） |

### 4.6 Streamlit 前端

两个页面：**💬 知识问答**（对话式，引用卡片展开）、**📄 文档管理**（上传进度条、文档列表、删除）。仅调用 FastAPI 接口，不直接碰后端模块——保持架构干净。

### 4.7 工程化

- `.env.example` 提交，`.env` 进 `.gitignore`
- `loguru` 结构化日志：`request_id` 贯穿一次问答全程（检索耗时 / LLM 耗时 / token 数）
- Dockerfile 多阶段构建；`docker-compose.yml` 一键起 `api` + `web` 两个服务
- pytest：解析器对样例文件的断言测试 + 检索冒烟测试

### 4.8 阶段1验收标准

- [ ] 上传 3 种格式文档，入库成功且 chunk 元数据完整
- [ ] 提问后 5 秒内返回带引用的答案，引用可对应到真实文档页码
- [ ] 知识库没有的问题，模型回答"资料中未提及"而非编造
- [ ] Postman 可完整调试全部接口
- [ ] `docker compose up` 一键启动全栈

## 5. 阶段2 · 优化版详细设计（2-3 周，面试重点）

### 5.1 多路召回（Hybrid Retrieval）

**为什么**：纯向量检索对专有名词/型号/错误码这类精确 token 召回差（embedding 把语义相近但词不同的内容拉近，却把词面相同的专有名词"平均"掉了）。

**设计**：

```
                ┌─→ 向量检索（Chroma, Top-8）──┐
   用户查询 ────┤                             ├─→ RRF 融合排序 → Top-5 进入重排
                └─→ BM25（rank_bm25, Top-8）──┘
```

- BM25 用 `jieba` 分词后建内存索引（阶段1入库时同步维护），中文必须分词，否则 BM25 退化成整串匹配
- **RRF（Reciprocal Rank Fusion）**融合：`score = Σ 1/(60 + rank_i)`，无需调两路分数的权重，比线性加权稳
- 面试考点：为什么不用加权分数融合 → 两路分数量纲不可比（cosine ∈ [0,1] vs BM25 无界），RRF 只用排名，天然免疫量纲问题

### 5.2 重排序（Rerank）

- 模型：`BAAI/bge-reranker-large`（Cross-Encoder，输入 query+passage 拼接，输出相关性分数）
- 流程：召回 20 条 → rerank 打分 → 取 Top-3-5 进 prompt
- **Cross-Encoder vs Bi-Encoder**（必考）：Bi-Encoder（BGE 向量）两路独立编码可预计算、快但粗；Cross-Encoder 双塔拼在一起过注意力、准但每次都要实时算 → 所以只能用在召回后的小集合上，这是"先粗排后精排"的经典漏斗
- 显存不够时降级 `bge-reranker-base` 或用 DashScope 的 rerank API

### 5.3 查询改写

多轮对话中的两层改写（合一次 LLM 调用完成）：

1. **指代消解**：结合 chat history 把"那它的第二条呢？"改写成独立完整的查询
2. **HyDE**：让 LLM 先生成一段"假设性答案"，用假设答案的 embedding 去检索——因为**答案和文档的向量空间距离，往往比问题和文档的距离更近**（问句和陈述句的表述差异）
3. 落地策略：HyDE 与原始 query **双路召回**再融合，不直接替换（HyDE 在事实型问题上可能跑偏）

### 5.4 会话记忆

- 会话维度 `session_id`，Redis/内存 存最近 N 轮（N=6，按 token 预算截断）
- Prompt 结构：`system + 检索上下文 + 历史轮次（压缩版）+ 当前问题`

### 5.5 检索评估体系（最大加分项）

- **自建测试集**：30-50 条 `(question, golden_doc, golden_chunk)` 三元组，从真实文档里人工出题
- 指标脚本（`eval/evaluate.py`）：

| 指标 | 定义 | 度量什么 |
|---|---|---|
| Recall@K | golden chunk 是否出现在 Top-K | 检索能力 |
| MRR | golden 排名倒数 | 排序质量 |
| 命中率 | 答案引用是否包含 golden doc | 端到端 |
| 忠实度 | 答案是否被检索内容支撑（LLM-as-Judge） | 幻觉率 |

- **AB 实验**：`纯向量 vs +BM25 vs +Rerank vs +HyDE` 逐项叠加，出一张对比表——这张表就是面试时"我的优化让召回率从 X% 提升到 Y%"的数据来源

## 6. 阶段3 · 生产化（第 4 周起，按需）

1. **向量库升级**：Milvus（千万级向量、分布式）或 pgvector（团队已有 PG、量级中等时最省事），沿用抽象接口，只写新 adapter
2. **扫描件 OCR**：PaddleOCR 预处理链路
3. **权限隔离**：collection 按部门隔离 + 文档级 ACL 元数据过滤（Chroma 的 `where` 过滤即是雏形）
4. **可观测性**：接入 Langfuse（自部署）追踪每次 RAG 链路的 trace
5. **高可用**：Gunicorn + Uvicorn worker、模型推理独立成服务

## 7. 里程碑与风险

### 7.1 里程碑

| 周 | 交付 |
|---|---|
| W1 | 工程骨架 + 解析/分块/入库链路 + 单测 |
| W2 | 问答链路 + FastAPI 全接口 + Streamlit + Docker，阶段1验收 |
| W3 | 混合检索 + Rerank + 会话记忆 |
| W4 | 查询改写 + 评估体系 + AB 报告，阶段2验收 |

### 7.2 风险与预案

| 风险 | 预案 |
|---|---|
| BGE-Large 本地跑不动（无 GPU） | 降级 `bge-small-zh-v1.5`（效果损失约 2-3 个点）；或用 DashScope text-embedding API |
| 扫描版 PDF 无文本层 | 阶段1 明确提示不支持，阶段3 OCR |
| DashScope 限流 | 指数退避重试 + qwen-turbo 降级链 |
| BM25 索引重启丢失 | 持久化为 JSON（阶段3 换 ES） |
